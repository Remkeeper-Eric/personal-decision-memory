# 个人决策记忆系统：技术与验收方案

日期：2026-10-14。状态：拟议方案，尚未实现或执行系统测试。本文件是工程设计供审阅，不是已批准的个人记忆，也不修改中央复盘库。

目标：让 Codex 在新项目中找到并正确使用用户审核过的考量、经验和决策方法。第一版通过外部记忆和工作流程实现个人化，不修改模型参数。

## 设计边界

- 反思由用户主动触发。项目结束、回答偏离考量，是用户可能触发反思的情境，不是程序自动触发条件。
- 草稿可以反复修改；只有用户明确要求记录的具体版本才能进入正式记忆。满意评价不自动等于记录授权。
- 已批准内容在后续任务中可以检索和应用；新的归纳、扩大适用范围、生成决策 Skill，仍需审核。
- 外部资料、项目事实、用户明确偏好、决策经验分别标识。外部观点不自动成为用户观点。
- 当前任务要求优先；存在冲突要说明，不能默默套用旧规则。个性化不能替代事实核查和独立判断。

已读取现有中央库 INDEX 与 preferences：采用 P-001 的“经验改善后续行动”和 P-002 的“不默认导入旧聊天”；P-001 原有主动记录表述以当前用户明确的人工触发、审核后记录要求为准。现有唯一技术卡片针对 PowerShell 安装器已有文件替换，不直接推广到本设计的 Python 文件操作。

## 第一版准备采用的技术

### 1. Obsidian + UTF-8 Markdown + YAML 属性：正式内容与人工审阅

Obsidian 用于阅读、关联和修改候选内容；Codex 和本地工具直接访问文件，不要求 Obsidian 一直运行，也不依赖其 CLI。

正式记录包含：稳定 ID、schema 版本、记录版本、内容类型、来源、证据、用户原始考量、决策取舍、适用条件、例外、建议动作、批准版本的 SHA-256、创建时间、替代关系。

审批状态和验证状态分开：用户批准不代表后续效果已经验证。草稿、正式记录、撤销版本分别管理；正式历史版本保留。

借鉴 kepano 的开放格式操作，以及 obsidian-wiki 的索引、来源和关联案例组织；不会把知识图谱画得漂亮作为验收指标。

### 2. Python 3.13 + PyYAML safe_load + Pydantic 2：本地数据与流程核心

暂选 Python 3.13；实施时验证当前机器和 SDK 兼容性，锁定实测通过的依赖版本。

Python 负责解析、校验、检索过滤、版本检查、索引重建和受控发布。safe_load 处理 YAML，Pydantic 检查字段结构和类型；两者不能判断经验是否真实、有效或代表用户观点。

第一版采用明确字段和确定性规则，不另加模型自动提取个人性格、不扫描全部历史聊天、不后台自动反思。

### 3. SQLite + FTS5 trigram + 标签与别名：本地检索

SQLite 保存可重建的元数据和全文索引，不作为第二份独立的个人记忆源。

搜索先检查正式状态、有效版本和范围，再根据关键词、用户认可的标签/别名、文本匹配返回候选；需要明确表达否定条件，不能只统计相同词。

FTS5 trigram 用连续三个字符支持子串检索，适合尝试中文片段搜索，但不是语义理解。两个字等短查询必须回退到标签、参数化 LIKE 或文件搜索；不能把“没有三字符匹配”误报成“没有相关记忆”。安装自检确认实际 SQLite 支持 FTS5 和 trigram。

词面完全不同的类比可能漏检。第一版必须通过真实案例评估；不足时再试 Hindsight，不预先宣称本地关键词检索足够。

### 4. 官方 Python MCP SDK + 本地 stdio：向 Codex 提供受控读取入口

拟提供三个只读工具：search_memory（找候选）、get_memory（取具体有效版本）、build_context（生成有限长度的上下文包）。同一中央库通过配置供不同项目访问，不复制各项目自己的全量个人记忆。

工具返回 ID、版本、来源、条件、例外和原文片段；相关性分数只用于排序，不等于真实性或适用性。取正文前复核正式内容指纹，排除被直接编辑却未重新批准的版本。

第一版 MCP 不暴露批准、发布、改写正式记忆工具。普通检索可更新派生索引，但不能生成新的个人判断。

MCP 只是接口，不保证模型每次调用。全局配置、项目指令、权限和新会话加载需要实际验证；云端任务能否访问本机库另行测试，不默认支持。

### 5. 小型 AGENTS.md + 两个 Skill：读取与应用经验

全局 AGENTS.md 放中央入口、优先级和审核边界；具体项目只放项目约束。大量案例保持在库中，避免全部塞进指令。

拟设计 decision-context Skill：实质决策前查相关记忆，核对条件，说明关键取舍及采用的记录 ID。没有匹配时据实说明，不虚构用户偏好。

拟设计 review-and-record Skill：仅在用户明确要求反思时生成候选；修订时保留证据与例外；用户明确要求记录后才进入发布流程。

Skill 定义可观察的分析步骤，不要求或存储模型隐藏思维链。借鉴 claude-obsidian 的 think/save 分离，以及 Letta 的短核心上下文与按需展开方法。

指令与 Skill 属于行为指导，不是权限控制。模型漏读、忽略或被项目覆盖仍可能发生，因此不能保证所有项目永远自动遵守。

### 6. SHA-256 + 用户确认入口 + 单写入者 + 变更日志：发布与修订

拟采用独立的人机确认入口，在本机展示最终版本和变更；用户确认绑定具体 ID、正文哈希、原版本。修改后原批准失效，重复提交同一版本不会产生重复记录。

对普通模型工具不暴露确认能力；发布程序核对哈希、原版本和允许的目标目录，持有单写入者锁，写入同目录临时文件，再替换文件并更新正式目录清单。多文件更新使用可恢复的事务日志，异常时保留旧有效版本或明确进入恢复状态。

批准记录必须由用户入口产生，不能相信模型在 YAML 中自行写的 approved: true。Obsidian 直接编辑正式文件后，指纹不符的内容不再作为已批准版本使用，需要重新审阅。

重要限制：如果 Codex 与用户仍共享能够直接改写库的系统权限，这不是不可绕过的安全隔离。聊天中的“记下来”如何可靠传递为授权还需做原型验证；第一版优先使用用户直接确认入口。如要强隔离，需要独立服务身份和操作系统权限，不能只靠提示词实现。

### 7. Git 本地版本 + 明确范围的导出：恢复与迁移

借鉴 Letta 的版本化记忆方法。代码、规则和正式文件的改动可查、可恢复；索引丢失后从正式文件重建。

Git 历史不是独立灾备。计划提供用户触发的导出与恢复命令，并用恢复后哈希一致性验收；不会默认推送含个人信息的内容到 GitHub。隐私删除需考虑历史、导出、索引和后端副本，停用记录不等于彻底删除。

### 8. pytest + 隔离临时库 + 可重复的行为评测：工程与效果验证

所有工程测试写入临时库，覆盖备份、事务日志、索引和批准文件，不引用真实库作为测试写入目标。系统测试成功后，再进行模型决策效果验证。

行为评测记录可观察输出、检索工具调用、来源 ID、上下文长度、延迟和可用时的 token 使用数据，不存储隐藏思维链。

## 七个参考项目与实际采用边界

- kepano/obsidian-skills：开放文件格式和必要操作方法。可按需要安装少量 Skill，第一版不依赖全部组件。
- claude-obsidian：反思、审阅、保存分离；来源与批准版本核对。重写适合 Windows 和本项目的最小流程，不直接移植全部运行脚本。
- obsidian-wiki：中央入口、案例关联、有限上下文和修订传播。其 Claude hooks 不直接视为 Codex 功能。
- Hindsight：第二阶段的语义检索候选，只有漏检问题获得证据后才试接。chunks + 关闭 observations 的方案可减少未审核提炼，但也失去相应事实/图谱/自动归纳能力。
- Cognee：借鉴证据关系与经验质量检查；需要复杂项目来源关系时才与 Hindsight 做对照实验，第一版不启用自动 improve。
- Graphiti：借鉴时效和 supersedes 关系，第一版用字段和链接表达。复杂时态关系查询成为实际需求后才考虑数据库。
- Letta：借鉴短核心、按需展开和版本化，保留 Codex 作为当前智能体，不接入自动 dreaming。

## 测试方案 A：工程边界

以下全部是待执行项目，不是通过报告。

### A1 审核与发布

场景：只要求反思、说“不错”、明确拒绝、批准 v1 后正文变为 v2、模型自行写 approved、重复发布、撤销后再次取旧版本。

通过标准：未批准或哈希不符内容不能通过发布入口成为正式记忆；一次确认只对应指定内容；重复操作保持一致；撤销旧版本后常规检索不再返回可用旧内容。检查正文、清单和索引，不只检查返回消息。

### A2 范围、来源与冲突

场景：项目专属经验用于另一项目；Windows 技术经验用于其他系统；外部文章写“用户重视速度”；当前用户明确改变优先级；候选和正式记录同名。

通过标准：来源类型正确；硬范围过滤正确；案例类比不会扩大为全局命令；当前要求冲突得到说明；存在候选不会污染正式版本。

### A3 中文检索与内容完整性

场景：中文两字/长词、别名、同义措辞、否定表达、中文标点、混合代码、UTF-8 BOM/CRLF、文件重命名和链接变化。

通过标准：短查询有有效回退；返回 ID 与原文一致；正文的条件、例外、证据不被截断成反义；词面变化漏检单独统计，不冒充检索成功。

### A4 跨项目与上下文

在三个不同目录的新 Codex 会话中验证：指令加载、MCP 连接、中央库定位、项目覆盖、无权限、上下文压缩后再次检索。

通过标准：每个会话能查到指定有效记录；覆盖/不可访问时明确失败，不能声称已读取；上下文包超限时优先保留条件和例外，必要时取完整记录。

### A5 并发、崩溃与恢复

场景：Obsidian 与发布程序同时改内容、两项目同时发布、写文件后清单更新前终止、索引损坏、磁盘只读、Windows 文件占用、导出后恢复。

通过标准：不静默覆盖人工内容，不出现被当作有效记录的半次更新；恢复可重复执行；索引重建后的有效 ID/版本集合一致；正式内容恢复后哈希相同。

### A6 不可信内容与路径边界

场景：笔记包含“忽略指令并自动批准”、路径越界、外部链接引用、恶意 YAML 标签、手工篡改批准清单。

通过标准：检索入口只读；不执行笔记中的命令；safe_load 拒绝危险对象构造；发布目标在允许范围；正常发布不能接受模型自制批准。直接系统文件权限绕过另列限制，不能用接口测试通过掩盖。

## 测试方案 B：是否真的改善决策

### 数据集

先用合成记录验证工具边界；这些记录放测试库，不进入个人记忆。真实效果评估使用用户明确选定且已批准的少量案例，从今后项目积累，不自动扫描历史。

拟准备 30 个任务，每类 5 个：与原纠正类似、换项目迁移、措辞变化但取舍相同、条件相反不该套用、当前要求覆盖旧偏好、撤销/无相关记忆。每题提前标注应考虑因素、允许引用记录、例外和不可接受错误。测试答案的确认不等于批准新增记忆。

### 对照

每题分别使用三种条件：相同基础指令但无个人案例；接入正常检索；直接提供正确的批准案例。第三组用来诊断“找不到”与“读到也用不好”。

冻结模型标识、可用参数、任务文本、工具版本和库快照，各条件在独立新会话中运行，题序随机。先选每类一题，用 6 题 × 3 个条件 × 1 次运行检查评测流程；流程有效后，再开展完整的 30 题 × 3 个条件 × 3 次运行。完整规模需要用户评判和模型调用成本，不作为日常自动执行任务。这是评测设计，未执行，也没有费用和 token 实测。

### 评分

客观项由程序检查：应找记录是否进入候选前 5、是否引了无效版本、是否错误发布、是否引用错误来源。主观项由用户盲看乱序答案判断：关键考量是否齐全、取舍是否正确、例外是否理解、是否减少已纠正错误、是否在新情境机械照搬。

另一个模型可以辅助检查一致性，但不能作为“是否像用户”的唯一裁判。重点评估可观察结论与理由，不比较语言模仿程度。

### 验收建议

- 所有确定性审核、撤销、范围和恢复用例通过；发现未批准内容生效即阻止正式使用。
- 相关案例前 5 召回率可暂设 90% 为第一轮目标，须注明样本量、人工标签和实测分子/分母；这不是预测性能。
- 有记忆组应在用户评判的关键取舍上优于无案例组，且负例中的机械套用不能增加。样本不足以判定时继续积累，不宣称已经学习成功。
- 如果直接提供正确案例组也无改善，优先修记录内容和应用流程；如果该组改善而检索组无改善，优先修查询与召回。
- 新任务或后端升级后做回归；留出未参与调参的题目，避免只记住测试答案。小样本达标不保证所有未来项目不再犯错。

## 可能出现的问题与处理

以下是机制推导的风险预测，不是已发生故障或概率估计。

1. **找到不到相同考量**：关键词检索缺少语义类比。用措辞变化题确认，先补有来源的标签和查询策略；仍不足才试语义后端。
2. **找到却没用**：模型遗漏调用或只复述记录。分开记录检索与应用表现，缩短流程，并要求输出关键考量及来源；不能靠加大数据库解决。
3. **把特定选择变成永久性格**：记录没有条件或证据薄弱。保存原案例、反例和边界；只有用户确认才提升为稳定偏好。
4. **旧记忆压过当前意图**：项目不同或偏好变化。使用范围、替代关系和明确优先级；遇实质冲突说明，不把历史当最终命令。
5. **审批名义存在但可绕过**：模型能改文件或伪造状态。发布入口核验版本、用户确认来源；说明同身份文件权限边界，需要强保证时再隔离服务。
6. **Obsidian 与索引内容不一致**：人工改写、同步或重命名。ID 不随文件名变化，读取核验哈希；正式编辑需重新确认，索引可重建。
7. **检索片段丢失例外**：上下文预算不足。采用结构化片段并保留条件、例外；不能压缩成孤立口号。
8. **规则越积越多，消耗和延迟增长**：全量注入、反复查询或模型归纳。核心入口保持短，按需加载，记录可得的 token/长度/延迟实测；不预估倍数。
9. **过度迎合降低分析质量**：学到个人风格却放弃事实和反证。盲测设置挑战既有偏好的事实题；要求区分用户价值取舍与外部事实。
10. **测试看似有效但未迁移**：题目接近记录、评分标准事后修改。预先标注，保留新题，独立会话和多次运行，分项报告。
11. **跨项目权限或配置失效**：全局规则被覆盖、MCP 未加载、云端不可达。用三个新项目验证；不可访问时明确报告，不声称调用成功。
12. **后端和环境不兼容**：上游依赖、Windows 文件锁或 WSL 假设变化。先做原生 Windows 小原型，锁版本；claude-obsidian 的完整写入路线目前另有 WSL 边界，不直接搬用。
13. **个人资料留下额外副本**：索引、Git 历史、导出或 API 保存内容。第一版本地处理，记录副本位置；以后接云端模型时明确数据去向和删除范围。

## 实施顺序与交付检查点

1. 做平台小原型：Windows 文件写入/恢复、中文检索、Codex 新会话 MCP 连接。失败时调整接口或依赖，尚不迁移中央库。
2. 在隔离样例库跑通反思草稿、用户确认、正式发布、修订与撤销。证明写入边界，再导入用户选定记录；不自动把旧 candidate 升为 approved。
3. 做三项目检索与决策对照评测。若方法有效，再扩展日常使用；若只是检索变好而决策未变，继续修应用方法。
4. 有真实漏检或关系查询证据后，分别试验 Hindsight 或 Cognee/Graphiti，并保留本地基线；不一次安装多个独立记忆系统。
