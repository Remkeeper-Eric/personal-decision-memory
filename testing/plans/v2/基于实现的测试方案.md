# 基于当前实现的测试方案 v2

2026-10-14。状态：方案已准备，未启动本方案的测试。替代 v1 的默认执行安排；保留 v1 作为方案历史。本文是工程测试资料，不是个人经验、候选或正式记忆。

## 结论与调整理由

默认采用：程序检查状态边界 → 固定语料检查检索 → 少量全新 Codex 会话检查应用 → 用户检查真正的个人化效果。

不把样例生成对话和模拟用户评审对话设为必经环节。生成器适合补充变体；评审模型适合辅助查遗漏。批准状态、检索 ID、版本和文件变化由程序核验；用户自己的取舍由用户核验。AI 评审不能同时承担这两类判断。

v1 过早围绕 C/A/B 对话组织流程，并把已有 token 项目规则放在首轮。检验该规则有价值，但不能证明外部记忆对后续决策有贡献。本版把当前实现中尚未充分验证的检索与应用放在前面。

## 代码依据与现有证据

- `src/decision_memory/store.py:284`：检索是 SQLite FTS5 trigram、标签/别名和子串评分，没有语义向量检索。连续中文通过正则得到较长词项；同义改写、长问句和相近记录之间的排序需要实测。
- `src/decision_memory/models.py:78`：项目范围和环境由程序过滤。`applies_when` 和 `exceptions` 的自然语言含义需要 Codex 判断，不能把过滤通过等同于适用。
- `src/decision_memory/store.py:330`：上下文超限时整条记录进入 omitted，不自动压缩。后续是否正确调用 get_memory 尚需行为测试。
- `tests/test_store.py:68`：external_note 测试核对返回类型，没有证明模型会正确区分外部观点与用户观点。
- `tests/test_mcp.py`：验证 SDK 客户端从三个工作目录调用接口，没有证明三个真实项目里的 Codex 会主动检索并正确应用。
- 之前 44 项工程测试通过；本次方案调整没有重跑，不能当作新增覆盖。当前一次正式 MCP 查询返回 memories=[]、warnings=[]，仅说明该查询没有返回匹配经验。

以上揭示覆盖缺口，不代表已经测出缺陷。

## 第一阶段：可以由程序判断的边界

沿用现有 pytest 体系，测试库、批准清单、索引、日志、事务和备份全部置于独立临时根目录。测试夹具的“批准状态”只用于模拟数据状态，不表示用户认可合成偏好。不得对生产审核页面或生产发布接口操作。

现有用例覆盖候选不参与检索、具体版本与哈希绑定、修订、撤销、正文篡改、范围过滤、导出恢复和只读 MCP。没有相关修改时不反复运行全套；新增边界用例或修复时运行受影响的检查，并按必要性完成回归。

需要明确报告两个不同层次：

1. 接口是否允许未经显示版本确认的发布，由隔离测试检查。
2. Codex 是否把“不错”“继续讨论”“模拟评审通过”误解成保存请求，由实际对话流程检查。

接口正确不能证明模型从未擅自生成候选；输出声称“未保存”也不能替代文件差异证据。

## 第二阶段：固定语料的检索验收

首轮优先执行这一阶段，不创建新聊天。它用现有 Store 接口即可实现，不需要新增向量数据库或接入模型。

准备三条明确标注为合成数据的记录：

- SYN-M01：小工具由非技术同事维护时，常见修改优先有图形入口；全是开发者维护且批量处理优先时例外。范围 SYN-team-tools，验证状态 unverified。
- SYN-M02：只用于 SYN-crawler / windows 的另一条经验，作为范围和环境干扰项。
- SYN-X01：与维护和操作方式有关的 external_note，用于检查相近内容的排序及后续来源区分；不代表用户偏好。

冻结记录正文、标签、别名、项目范围、环境和哈希，以及每题的预期相关 ID、禁止返回 ID、允许的不确定结果。条件性经验在例外场景中仍可能是相关资料：应区分“该检索到以便核对例外”和“该应用其中的默认动作”。

首轮 12 项检查，每项采用独立或恢复后的库快照：

1. 用记录中的关键词查询，检查基本召回。
2. 用完整自然中文问句查询，检查连续文字是否影响召回。
3. 用记录正文和别名中没有的同义表达查询，检查措辞迁移。
4. 加入多个考量和相近干扰记录，检查目标是否进入默认前五条及排位变化。
5. 描述开发者维护、批量处理场景，检查能否取得含例外的相关记录；不能预设应返回空。
6. 描述用户当前明确选择命令行的场景，检索仍可返回相关经验；是否应覆盖旧建议留给行为测试。
7. 查询项目与 SYN-M02 范围不符，断言其不得返回。
8. 查询环境与 SYN-M02 不符，断言其不得返回。
9. 目标只有草稿，断言 search、context、get 不得把它当正式记录。
10. 目标已修订为 v2，断言普通读取只返回当前有效版本。
11. 目标已撤销，断言普通检索排除它。
12. 目标因预算限制整体省略，断言 omitted 含 ID，随后 get 能取得完整条件与例外。

记录实际查询、参数、返回的 ID/版本/排名/警告、遗漏项、耗时和返回字符数。字符数不是 token；排名分数不是可信度。

预先固定必需与探索项：第 1、7–12 项属于基本能力或状态边界；第 2–6 项揭示检索能力边界。探索项失败不能临时改名为通过。即使全部合成题通过，也不宣称理解真实用户。

把首轮 12 项原始输入输出与差异报告交给用户后停止，等待复核。不要看完结果再增加别名并覆盖旧结果。若需要调整索引或别名，保留原始失败，另存修改与回归轮次，并用未参与调整的新题复测。

## 第三阶段：实际 Codex 的检索和应用

先准备并验证独立测试只读 MCP。当前注册的是生产只读入口，测试专用入口尚未建立。不得通过改写生产 MCP 路径来切换库，也不得因为对话是新的就宣称工具、规则和上下文已隔离。

进入这一阶段时先解决连接方式，并核对实际工具参数、返回来源、测试库路径以及文件写入范围。若无法做到可靠的测试入口隔离，先用明确标注的给定工具结果测试应用能力；这样的结果不算实际 MCP 检索通过。

第一个行为案例选取 SYN-M01 适用、且题目没有直接提示该偏好的情境。准备三个独立执行会话：

- 空库组：同样的任务、规则和只读接口，库为空。
- 检索组：同样条件，测试库含 SYN-M01，由 Codex 自主查询。
- 直接资料组：直接提供完整 SYN-M01，绕过检索；来源标记为给定测试资料，不允许声称是工具召回。

先由三组结果定位问题，不立即增加多个评审对话。直接资料组是诊断用对照，提示方式本身也可能影响行为，不能作为严格的单一变量因果实验。

判断规则：

- 检索组没有取得目标记录，优先定位是否调用、项目/环境参数、查询用词和排名。
- 已取得完整目标但没有核对条件、例外或没有改变取舍，定位应用流程或记录可操作性。
- 直接资料组能用、检索组不能用，说明检索或上下文组装值得优先检查。
- 空库组本来就作出相同合理选择，记忆可能被正确引用，但该题没有建立决策增益。
- 检索组有准确 ID/版本引用，却没有在分析或方案中体现相关考量，不能只凭引用判应用成功。

三组完成即交付原始记录并停止。用户复核后再做例外成立、当前要求覆盖旧建议、external_note 仅作外部资料三个边界案例。边界案例每题使用新会话，优先检验正常检索路径；发生难以归因的失败再增加直接资料对照。

首次表现仅是案例证据。对关键结论，在用户同意下一轮后用新的同类任务或重复运行检查稳定性，不用一次输出估计泛化准确率。

## 第四阶段：反思与审核流程

反思流程需要一条分步推进的会话，因为本来就要验证对话状态；跨项目迁移则需要新会话。两者不能采用同一种“全部清空上下文”的测试方法。

在隔离测试范围中依次检查：

1. 明确要求反思、先讨论、不保存：应讨论遗漏、取舍和边界，不生成候选。
2. “分析不错，继续补充例外”：应继续讨论，不能把认可当成保存授权。
3. 明确要求形成测试候选：只产生隔离候选，不声称正式生效。
4. 候选修改后：工程接口必须要求核对新的具体版本，旧显示或确认不能沿用。

模拟用户话语明确标注测试身份，不表示真实偏好认可。程序核对前后文件变化和状态，模型只辅助检查分析是否有遗漏。真实用户的审批权不交给模拟 B。

## 第五阶段：真正的个人化验收

前提是用户亲自批准至少一条真实经验。取用户指定的一个来源作为样本，不自动扫描旧聊天。由用户认可适用条件、例外及关键判断标准。

准备没有在该条经验提炼或修改中用过的新任务：相似场景、范围成立的另一个项目、例外场景。新会话不再次提示偏好，记录实际召回及决策。尽量使用同样接口的空库对照，区分模型常识、已有 AGENTS 规则与新增记忆的作用。

用户主要判断：是否体现自己的重要考量、是否误用例外、是否保留必要取舍、是否少犯此前纠正的错误。用户可以指出符合或不符合的具体段落，不要求用户接受模型给出的总分。

准确记住记录证明检索；依条件改变取舍证明应用；用户认可新情境中的判断且具有持续表现，才支持个人化效果。外部记忆仍是运行时参考，不表示改变了模型权重。

## 可选的生成器与评审者

- 生成器：在基本题冻结后一次性补充改写和困难反例，保留部分新题不用于修正检索或提示词。生成器不知道已测输出，以免围绕失败结果出题。
- 评审者：使用明确标准、先于看到结果冻结标准，辅助指出漏项和证据不足。必要时隐藏组名并打乱输出顺序，但保留影响判断的来源事实。
- 两者都不是首轮必要配置，也不因为模型扮演用户就获得用户的价值判断或批准权。

这保留了此前 A/B 提议中“职责分开、全量记录、用户复核”的优点，减少可由程序直接核验的重复模型工作。

## 日志、控制变量和停止条件

实际运行目录使用 `testing/runs/<轮次>/`，本地保存且 Git 忽略。保存：冻结语料/题目/标准版本及哈希、运行条件、实际输入、完整可见输出、工具调用及返回、文件前后差异、客观检查、AI 初评（如有）、用户复核（到达后）。不保存隐藏思维链或认证令牌；原始证据被截断时标为不完整。

模型、规则、Skill、接口和库快照的可取得配置均记录；无法取得的字段标为未知。改规则、改语料、换模型和修检索分别记录，避免同时改变多个因素后无法归因。额外技能可能访问文件或写日志，不能把 MCP 只读当成整个 Codex 进程只读。

任何生产写入、错误库来源、关键证据缺失均停下并报告。测试报告状态统一为待用户复核，用户查看报告不自动授权下一轮。发现问题先给出归因和修复建议，不自动修改正式偏好或扩大实现范围。

对当前每次检索都会校验记录并重建索引的实现，后续单独增加合成库规模和并发检查。先报告随规模变化的耗时、返回大小和故障；没有用户响应时间目标时不编造性能验收阈值。

开始采用多会话、大量重复试验或全文资料对照前，根据实际规模判断是否可能显著增加 token。若符合项目提醒条件，实施前明确提醒，简述原因，不新增审批。离线 Store 检索不调用模型，但准备题目、审阅报告和真实会话仍有模型消耗，不能把整个方案称为零 token。

## 建议的下一步

先准备三条合成记录和冻结的 12 项检索/状态样例，建立离线可重放测试入口，执行一轮后交付。检索是否可用先得到证据，再决定进入少量真实会话对照或修复检索。当前只是方案调整，没有启动这些测试、创建对话或写入个人记忆。
